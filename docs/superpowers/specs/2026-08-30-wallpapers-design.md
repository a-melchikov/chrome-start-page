# Дизайн обоев стартовой страницы

Статус: согласовано пользователем 2026-08-30.

## Контекст

Сейчас оформление дашборда включает системную, светлую или тёмную тему и
произвольный цвет фона. Настройки хранятся в конфиге версии 2 по ключу
`local:dashboard-config`, применяются в `App` и изменяются в диалоге
«Оформление».

Новая возможность должна добавить обои из локального файла или HTTPS-ссылки,
не нарушая локальную модель данных, совместимость сохранённых дашбордов,
очередность записей и ограниченный набор разрешений расширения.

## Цели

- Устанавливать одно фоновое изображение из локального файла или по HTTPS URL.
- Сохранять локальные байты без потерь и не переписывать их при каждом
  сохранении виджета.
- Проверять новый источник до переключения и сохранять прежние обои при ошибке.
- Заполнять изображением весь viewport с центрированием и обрезкой краёв.
- Поддерживать PNG, JPEG, WebP, GIF, AVIF и SVG.
- Сохранять совместимость с конфигами версий 1 и 2.
- Не добавлять `host_permissions`, сетевой кеш или backend.

## Не входит в объём

- Слайд-шоу, несколько одновременно сохранённых обоев и расписание смены.
- Настройка позиции, масштаба, размытия, затемнения или прозрачности.
- Редактор кадрирования и визуально-lossy оптимизация.
- Загрузка и локальное кеширование изображения по URL.
- Синхронизация, импорт/экспорт и установка системных обоев ChromeOS.
- Встраивание SVG-разметки в DOM или исполнение содержимого SVG.

## Пользовательский интерфейс

В существующем диалоге «Оформление» появляется раздел «Обои»:

- доступный выбор локального файла;
- поле HTTPS URL и кнопка «Установить»;
- компактный предпросмотр активных обоев;
- кнопка «Удалить обои»;
- состояние обработки и сообщение об ошибке с `aria-live`.

Выбор файла запускает проверку и сохранение. URL не запрашивается при вводе:
проверка начинается только после явного нажатия «Установить». Пока операция
выполняется, конфликтующие действия недоступны. Диалог можно закрыть; активная
проверка отменяется, а текущие обои не меняются.

Новый источник заменяет предыдущий только после успешной проверки и записи.
Кнопка удаления переключает фон на цвет и удаляет больше не используемый
локальный asset после успешного сохранения конфига.

Цвет фона остаётся обязательной настройкой и служит подложкой до загрузки
изображения и при временной ошибке URL. Обои не меняют выбранную тему. Текущие
непрозрачные поверхности контролов и карточек сохраняют читаемость; это также
проверяется вручную в обеих темах.

## Persisted-модель

Версия `DashboardConfig` повышается до 3. В `AppearanceConfig` добавляется
дискриминированный источник:

```ts
type WallpaperConfig =
  | { type: 'none' }
  | { type: 'url'; url: string }
  | { type: 'local'; assetId: string };

interface AppearanceConfig {
  theme: Theme;
  backgroundColor: string;
  wallpaper: WallpaperConfig;
}
```

URL хранится непосредственно в `local:dashboard-config`. Он должен быть
абсолютным HTTPS URL. Производное состояние загрузки и предпросмотра не
сохраняется.

Локальные данные хранятся отдельным WXT Storage item с ключом
`local:dashboard-wallpaper:<assetId>`. Конфиг содержит только UUID asset. Формат
payload имеет собственную версию и строгую runtime-валидацию:

```ts
interface LocalWallpaperAssetV1 {
  version: 1;
  assetId: string;
  mimeType:
    | 'image/png'
    | 'image/jpeg'
    | 'image/webp'
    | 'image/gif'
    | 'image/avif'
    | 'image/svg+xml';
  encoding: 'base64' | 'gzip-base64';
  originalByteLength: number;
  storedByteLength: number;
  data: string;
}
```

Base64 используется только как транспорт для JSON-совместимого WXT Storage.
Имя исходного файла, object URL, декодированное изображение и другие
производные данные не сохраняются.

## Миграция

- Конфиг версии 2 мигрирует в версию 3 с `wallpaper: { type: 'none' }`.
- Конфиг версии 1 сначала выполняет существующее преобразование `links` в
  `markdown` и нормализацию высоты Search, затем получает версию 3 и источник
  `none`.
- Тема, цвет, ID, содержимое и layout виджетов сохраняются.
- Некорректная структура текущей версии и будущие версии по-прежнему вызывают
  явную ошибку.

## Обработка локального файла

Допустимые MIME-типы: PNG, JPEG, WebP, GIF, AVIF и SVG. Расширению файла и
значению `File.type` нельзя доверять по отдельности: реализация проверяет
сигнатуру или структуру формата и успешное декодирование браузером. Для SVG
проверяется SVG-корень и декодирование как изображения; исходная разметка не
вставляется в DOM.

Порог равен `6 * 1024 * 1024` байт и считается до base64-кодирования:

1. Файл не больше порога сохраняется с `encoding: 'base64'` без изменения
   исходных байтов.
2. Для большего файла `CompressionStream('gzip')` сжимает полный поток байтов.
3. Если gzip-результат не больше порога, сохраняется
   `encoding: 'gzip-base64'`.
4. Если результат больше порога или сжатие недоступно/завершилось ошибкой,
   сохраняются исходные байты с `encoding: 'base64'`.

При чтении gzip-payload восстанавливается через `DecompressionStream`. Результат
должен иметь заявленный исходный размер и успешно декодироваться. Автотест
проверяет полное байтовое равенство до и после цикла сжатия.

В manifest добавляется обязательное разрешение `unlimitedStorage`. Оно нужно
для несжимаемых исходников и base64-overhead. Разрешение `wallpaper` не нужно:
функция меняет только фон новой вкладки, а не системные обои ChromeOS.

## Проверка URL

Сначала строка разбирается через `URL`; разрешён только протокол `https:` и
непустой hostname. Затем временный `Image` с `referrerPolicy="no-referrer"`
должен успешно загрузиться и декодироваться. Проверка имеет тайм-аут 10 секунд
и отменяется при новой проверке или закрытии диалога.

Проверка не использует `fetch` или `XMLHttpRequest`, поэтому расширению не нужны
широкие `host_permissions`. Успех браузерного декодирования является проверкой
формата удалённого ресурса; MIME-заголовок отдельно не читается.

После успешного сохранения URL не кешируется. При последующей временной сетевой
ошибке слой обоев показывает цвет фона, сохраняет URL и повторяет обычную
загрузку при следующем монтировании.

## Транзакционная замена и очистка

Операции с обоями получают отдельный асинхронный путь в storage repository и
хуке. Они не используют обычное оптимистичное частичное обновление appearance,
поскольку ошибка записи не должна визуально или персистентно уничтожать прежний
источник. Ожидающие debounced-изменения виджетов сначала согласуются с общей
очередью записей.

Установка локального файла:

1. Создать новый UUID и записать проверенный asset под новым ключом.
2. Сохранить актуальный конфиг, указывающий на новый UUID.
3. Переключить React state на подтверждённый конфиг.
4. Удалить предыдущий локальный asset, если он существовал.
5. Если шаг 2 не удался, удалить новый asset и сохранить прежние state/config.

Установка URL сначала проверяет изображение, затем сохраняет новый конфиг и
только после подтверждения переключает React state. После этого удаляется
предыдущий локальный asset. Удаление обоев сначала сохраняет источник `none`,
затем удаляет прежний локальный asset.

Ошибка удаления уже неиспользуемого asset не откатывает успешно переключённый
фон, но показывается пользователю. При загрузке repository удаляет orphaned
wallpaper items, на которые не ссылается текущий конфиг. Ошибка такой очистки
не блокирует валидный дашборд и выводится как предупреждение.

Если активный локальный asset отсутствует, повреждён, имеет неверный UUID,
формат, длину или не декодируется, изображение не передаётся в UI. Показываются
цвет фона и явная ошибка; сам конфиг не исправляется молча.

## Компоненты и поток отображения

- `storage/schema.ts` описывает конфиг версии 3 и `WallpaperConfig`.
- `storage/migrations.ts` валидирует и мигрирует v1/v2/v3.
- Отдельный wallpaper repository владеет ключами asset, кодированием,
  сжатием, декодированием, заменой и очисткой.
- `useDashboardConfig` координирует транзакционные wallpaper-операции с
  существующей очередью сохранений и сообщает UI состояние/ошибки.
- `AppearanceDialog` отвечает только за форму, предпросмотр и запуск операций.
- `WallpaperLayer` отвечает только за отображение проверенного URL или Blob.
- `App` остаётся composition root и соединяет appearance, слой обоев и
  Dashboard.

`WallpaperLayer` находится поверх цветовой подложки и позади Dashboard. Он
рендерит неинтерактивный декоративный `<img alt="" aria-hidden="true">` на весь
viewport с `object-fit: cover`, `object-position: center` и
`referrerPolicy="no-referrer"`. Локальные байты превращаются во временный Blob
URL; URL освобождается при замене источника и размонтировании.

SVG всегда остаётся в image-контексте `<img>`. JavaScript в таком контексте не
исполняется, внешние ресурсы SVG не загружаются, а ссылки не интерактивны.

## Ошибки и доступность

- Ошибка чтения, валидации, URL-проверки, обработки или записи отображается в
  диалоге и оставляет прежние обои.
- Состояние обработки доступно assistive technologies; кнопки имеют явные
  accessible names, а ошибки связаны с соответствующими полями.
- Escape и восстановление фокуса сохраняют существующее поведение `Dialog`.
- При временной ошибке уже сохранённого URL нет повторяющегося глобального
  alert на каждой новой вкладке: используется цветовая подложка, а состояние
  ошибки видно при открытии настроек оформления.
- Ошибки основного config/asset storage по-прежнему выводятся пользователю и не
  проглатываются.

## Тестирование

### Storage и domain

- Миграция v1 и v2 в v3 без потери виджетов и appearance.
- Приём валидных и отклонение некорректных вариантов `WallpaperConfig`.
- Валидация версии, UUID, MIME-типа, encoding, длины и base64 asset payload.
- Ветви «до 6 МБ», успешный gzip и fallback на оригинал.
- Байт-в-байт восстановление gzip-payload.
- Безопасная замена local → local, local → URL, URL → local и удаление.
- Откат нового asset при ошибке config save и очистка orphaned assets.
- Обычное сохранение виджета не записывает wallpaper asset повторно.

### React

- Установка, предпросмотр, замена и удаление через «Оформление».
- Запрос URL только после явного submit.
- Невалидный, HTTP, недекодируемый и timeout URL сохраняют прежний фон.
- Невалидный локальный файл и storage failure сохраняют прежний фон.
- Состояния загрузки, сообщения, фокус и Escape доступны.
- `WallpaperLayer` применяет cover/center, `no-referrer` и цветовую подложку.
- Blob URL освобождается при замене и unmount.
- Тема и изменение цвета продолжают работать и сохраняться как раньше.

### Проверка в Chrome

В распакованном extension проверяются PNG/JPEG, WebP, анимированный GIF, AVIF,
SVG, файл больше 6 МБ, рабочий и нерабочий HTTPS URL, удаление, перезапуск,
временное отсутствие сети, обе темы и длинный дашборд с прокруткой.

Перед передачей реализации выполняются:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm exec prettier --check .
```

## Критерии приёмки

- Локальный файл и HTTPS URL устанавливаются, заменяются, удаляются и
  восстанавливаются после перезапуска.
- URL не кешируется и не сохраняется до успешной проверки.
- Локальные исходные байты не меняются после сохранения и восстановления.
- Неудачная операция не уничтожает и не переключает прежние обои.
- Изображение заполняет viewport с центрированием и обрезкой без повторения.
- Цвет остаётся корректной подложкой при загрузке или ошибке URL.
- Конфиги v1/v2 мигрируют в v3 без потери данных.
- Сохранения виджетов не переписывают локальный wallpaper payload.
- Единственное новое manifest-разрешение — `unlimitedStorage`; широких
  `host_permissions` нет.
- Автоматические проверки и Chrome smoke check проходят.

## Рассмотренные альтернативы

### Файл внутри `local:dashboard-config`

Отклонено: проще и атомарно, но многомегабайтная base64-строка переписывалась бы
при каждом изменении виджета или appearance.

### Blob в IndexedDB

Отклонено: устраняет base64-overhead, но добавляет второй механизм persistence
в обход принятой WXT Storage boundary.

### Только лимит 6 МБ

Отклонено: не соответствует требованию сохранять исходник, если lossless gzip
не способен уложить его в порог.

### Загрузка URL в локальный кеш

Отклонено: противоречит выбранному поведению «хранить только URL», усложняет
разрешения, очистку и расход диска.
